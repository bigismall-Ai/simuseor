测速口径

探针从「能不能连」升级成「能不能连 + 有多快」

每个站测三条通路；每条通路给两个读数：延迟（建连到首字节）与吞吐（固定字节数计时）。

通路什么时候测测什么
直连总是测官方地址直连
镜像该站配置了镜像才测HF 的 hf-mirror、GH 的加速前缀；没配镜像就不测这一条（卡片里标「未配置」）
代理全局代理已配置、且该站允许经代理时才测该站未允许经代理就不测（卡片里标「未启用」）
项口径
延迟建连到首字节（TTFB），毫秒
吞吐用 Range 取固定字节数（≤ 256 KiB）计时，MB/s
轻量只打小文件 / 固定字节数的 Range 请求，绝不拿模型权重测速
取样每条通路取样 1 次，失败最多重试 1 次；单条通路预算 ≤ 8 s

如实说明：本轮所有速度数值都是示意值 —— 没有对任何站点发过真实测速请求，也没有发过真实可达性探测请求。 页面上的 MB/s 与延迟是写死的样例数据，用来展示「结论 + 速度」长什么样、怎么比较。 真落地时要用真实测速结果校准，阈值也要按实测分布重新定。

demo 不在设置页出现。它是本地假数据、不出网，做成一张站点卡没有意义；也不参与探测、测速与门控判断 （全网源都不通时由后台兜底切到它）。探测与门控的完整口径见规格文档。

状态数据流

探针 + 测速 → 缓存 → 后台链路

左栏那句「下载、列表都会通过探针的结果缓存走最快的那条」就是这条链路的全部要点；口径细节在这里与规格文档里。

① 探测 + 测速一轮探全部站，每站测直连 / 镜像 / 代理（该测的才测），每条给延迟与吞吐。
② 写缓存结论与速度写在同一份进程内缓存（不落 settings.json）。
③ 后台消费下载与列表读这份缓存：每站走它实测最快的可用通路；三条都不通的源被门控。
缓存口径取值说明
可达结论15 分钟慢消息才需要更快翻案
降级 / 受限10 分钟对端活着，只是被限流或要令牌
不可达结论3 分钟坏消息要更快翻案
立即作废改代理地址 · 改某站通路 · 改镜像地址 · 点「重新测试连通性」不必等 TTL
未探测不门控只有「不可用」才门控，否则第一次打开应用所有源都不出现
落盘不落盘状态放内存，settings.json 是配置不是状态

设置页不套用「灰置 + hover 提示」那套规则。那套是给发现页 / 下载页的筛选区用的（入口藏起来、鼠标悬停才说原因）； 设置页要把状态和速度直接写出来 —— 用户来这一页就是要看这个，不该再点一次才知道。

策略自动选择口径

按探针实测速度选最快的可用通路

参与判断的就是左栏这 6 个站。

层级规则说明
每站在该站测通的三条通路里选吞吐最高的一条；代理要快 20% 以上才选 —— proxy_speed > 1.2 × max(direct_speed, mirror_speed) 才走代理，否则走直连 / 镜像里更快的那个按实测吞吐比，不是按延迟比；直连与镜像都没测通时（base = 0）只要代理测通就走代理
发现 ＋ 下载同一站发现（列表）与下载两条通道走同一条：都吃探针实测选出的那条通路读同一份探针缓存结论，不分家；页面那句「下载、列表都会通过探针的结果缓存走最快的那条」就是这个意思
全局把各站实测吞吐按通路汇总（该通路可测的站求和），同样过 20% 门槛后选整体最快的一条作为默认策略策略卡上的「默认走 X」就是这条结论；每张站点卡显示的是该站自己那条 —— 直连被挡的站按自己的最快通路走，卡片上写明原因
兜底三条通路一条都测不通 → 策略显示「不可用」，并说明该源会被门控门控口径不变：只有「不可用」才门控，「未探测」不门控
手动点「解锁」后可强制指定 直连 / 镜像 / 代理，不受 20% 门槛限制门槛只管自动判定；手动指定后仍展示自动建议，指定通路对该站不可用时回退到该站最快的可用通路，并在卡片上标出回退

设置页不提供 sdk 入口：sdk 只在 huggingface 与 modelscope 真正实现，而且它不走普通下载器（没有分片、没有断点续传）。 后端的 sdk 分支保留不动，将来要用再说 —— 完整口径见规格 §3.6.1。
