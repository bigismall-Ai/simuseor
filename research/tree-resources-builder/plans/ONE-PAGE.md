## 一句话结论

这套白模体系真正的价值不是「模型好不好看」，而是「**可回读的相机与结构数据**」——机位、焦距、时序、关节、语义这些能被下游直接吃的数据。

所以下一步优先补**两件事**：① 把条件图通道补成下游真正消费的那几件；② 把运镜从「一次推镜」做成可复用的镜头库。资产该补，但边际价值排在相机和条件图后面。

## 现在有什么

六类东西的真实状态（都是仓库里已经落盘的，不是设想）：

| 类别 | 现状 | 缺口 |
|---|---|---|
| **人物** | 22 部件、3,344 面、1.74 m 的主角模型，SOMA 三个后端 CPU 实跑过 | 面部/口型/手部没细节；身份变体太少；服装是外挂一层壳，不是贴合多件 |
| **植被** | 树模型 + L-system 参数 + 1 件公共树减面到 74,097 面 | 树种配方只有 1 套；没有实例化表；没有分档 LOD 规则 |
| **道具** | 程序化 1 件（箱子）+ 公共件 9 件 | **最大的空洞**：1 件加 9 件，构不成「零件库」这一层 |
| **载具** | 一台车（车身放样、抽壳、门缝、独立门板、4 个轮、灯、内饰代理）+ 一条船 | 没有变体（同一拓扑换参数不可用）；零件库只有这一套；飞机/轮船没实跑 |
| **场景** | 一个街区 + USD 汇合层 + 布局/人群/特效参数文件 | 只有一个街区；没有分块 LOD；3 件减面后的公共件还没混排进去 |
| **运镜** | 一次推镜：4 个关键帧、87 个采样点、3.6 秒；入画率 100%，主体高度占比 52%，校验通过 | **只有 1 种镜头**：没有镜头类型库、没有可自动判定的构图指标、没有批量镜头包 |

另外三个关键数字：校验项 **16/16 通过**，导出回读 **24/24 通过**，512×512 三通道条件图渲染 **83.24 ms**（预算 1500 ms）。

## 接下来做什么

八个阶段（细节在 ROADMAP §4，每阶段都有交付物和验收方式）：

- **R0 契约统一** —— 先把「下游到底要什么」写成能自动校验的契约，并把跟 resources3D 的深度极性、上轴冲突裁定掉。**为什么最先**：它阻塞其余全部，契约不定，后面做出来也没法验收。
- **R1 条件图六通道** —— 补上 mask、lineart、pose 三张，凑齐六通道。**为什么第二个**：下游最通用的线稿系和人体姿态现在完全没有；而且要先知道补哪几个，才轮到动手。
- **R2 运镜体系化** —— 从「一次推镜」做成 9 类镜头 + 镜头包，每个镜头自带几个能自动判定的构图/运动指标。**为什么在 R1 之后**：镜头包要出条件序列，通道不齐就出不来。
- **R3 镜头库与资产库 schema** —— 把资产和镜头变成有 id、指纹、许可、验证状态、能被引用的一等实体。**为什么和 R1 并行**：它俩都只依赖 R0，可以同时开工。
- **R4 五类资产补全（道具优先）** —— 道具补到 20 件零件库，其余四类从「一件」扩到「一族」。**为什么在 R3 之后**：没有台账，新资产无处挂。
- **R5 最小导演台** —— 给人的离线界面：选镜头、选资产、看校验。**为什么和 R4 并行**：只依赖 R2 和 R3。
- **R6 与 resources3D 对齐** —— 两套工作接到同一份契约上，同相机同场景交叉渲染逐像素比对。**为什么靠后**：得先有 R0/R1/R3 的产物才有得比。
- **R7 云端 LLM 接入** —— 把「验证闭环」真实化，统计首次成功率与 3 轮收敛率。**为什么可以并行**：只依赖 R0 和 R3。

一句话记顺序：**先定契约（R0），再补通道（R1）和台账（R3），然后才谈镜头库（R2）、资产（R4）和界面（R5），最后才是跨仓库对齐（R6）和云端闭环（R7）。**

> **R8.0/R8.1 补充（2026-11-23）**：下游本地模型接入前，先把「中性灰白模 MP4 + 从几何量出的 prompt + 叙事时间线 + 参考绑定（v1 已绑，含 text-only 版）+ 本地模型 request + 31 项自检」做成闭环；三个镜头（推/环绕/跟）已 93/93 通过。细节见 `plans/R8-interface-probe.md`。

## 红线清单

以下这些**明确不做**，每条都给了理由和替代方案：

1. **不追求照片级有机细节**（毛发、皮肤、树冠写实、布料褶皱）——纯 CPU 加无生成式模型是硬天花板。→ 替代：代理表达 + 结构正确 + 运动正确。
2. **不去找「成熟开源参数化汽车底座」**——诚实边界：不存在。→ 替代：自建够用的 JSON 配方 schema，做同拓扑四个车身。
3. **不采集扫描件做近景主资产**——CPU 减面与修复成本高，实测高模件无法可靠分件。→ 替代：CC0 低模库（Kenney 为主）占位，Poly Haven 高模只作少量 hero。
4. **不做完整的资产库服务 / 数据库**——过重，本项目的产出量级不需要。→ 替代：JSON + 内容寻址 + 离线看板。
5. **不采用 OTIO 全量作为时间线模型**——OTIO 是**剪辑**时间线（track/clip/source range），我们是**镜头生成**时间线（相机轨迹 + 条件序列），语义不同。→ 替代：借它的字段命名和「外部引用」概念，自建 shot spec。
6. **不在本机跑下游预训练检测器**（HED/Midas/OpenPose）——我们输出的是「喂给下游的图」，不需要在本机跑下游；也违反「不下载模型权重」纪律。→ 替代：关键点图从自己的 SOMA 关节导出，线稿从 face_id 取轮廓。
7. **不用 Blender 做条件图渲染运行时**——bpy 5.0.0 本机实测可用，但启动开销大、渲染结果与 numpy 光栅不同源、跨解释器一致性成本高。→ 替代：继续用 numpy z-buffer，把 Blender 留作**下游验证工具**。
8. **不把语义 seg 扩成 100+ 类的 Segment Anything 体系**——我们只有 12 类资产，扩展成本高、收益低；下游 seg 通道对白模的价值主要在「可开关」而非精细分类。→ 替代：保持 12–16 类固定调色板。

## 要你拍板的 5 件事

这 5 个问题会实质改变后面做什么，建议在进 R0 之前定。细节在 ROADMAP §7。

1. **镜头库的数据模型：自造还是用现成的？**
   我的建议：自建 shot spec，**只借 OpenAssetIO 的数据模型**（asset_id + version + fingerprint，有 id 按 id 解析、没 id 按路径兜底），不引入外部运行时。
   选错会怎样：整套引入 OTIO 会把管线绑死到外部库版本上，而且语义错位（剪辑 clip vs 镜头包），下游接入反而更慢。

2. **条件图通道清单与深度极性？**
   我的建议：六通道（depth/normal/seg/mask/lineart/pose），深度改成「近=1 远=0」，与评估协议一致。
   选错会怎样：保持「近=0 远=1」的话，和 resources3D 的评估口径反向，交叉验证时每次都得显式转换，而且图发给下游时容易整个反了还不报错。

3. **道具零件库的来源策略？**
   我的建议：Kenney 为主 + 少量 Poly Haven hero（CC0、面数低、风格统一、可脚本化下载），特定缺口类目再用纯程序化兜底。
   选错会怎样：以 Poly Haven 为主则每件 5k–100k 面、要强减面、下载量大（已下载的 `island_tree_01` 单件 66 MB）；纯程序化则品类受限、风格单一。

4. **资产补全和镜头库，谁先做？**
   我的建议：镜头库优先（R2 先于 R4）——相机/条件图对下游控制力最强，也最阻塞下游接入。
   选错会怎样：资产优先的话，道具缺口虽然补上了，但镜头库拖后，下游能接上的时间点往后推。

5. **要不要把 Blender 引入为可选的下游验证工具？**
   我的建议：继续只用 numpy z-buffer，Blender 仅供人工验证；把引入 bpy 作为 R6 的一个**可选**分支（用现成 venv，不新增依赖安装）。
   选错会怎样：引入 bpy 会背上跨解释器一致性成本和启动开销，而且渲染结果跟 numpy 光栅不同源，对比时多一层不确定性。
