红线清单（明确不做，每条都有替代方案）

  • 不追求照片级有机细节（毛发 / 皮肤 / 树冠写实 / 布料褶皱）——纯 CPU 加无生成式模型是硬天花板。替代：代理表达 + 结构正确 + 运动正确
  • 不去找「成熟开源参数化汽车底座」——诚实边界：不存在。替代：自建 JSON 配方 schema，做同拓扑四个车身
  • 不采集扫描件做近景主资产——CPU 减面与修复成本高，实测高模件无法可靠分件。替代：CC0 低模库（Kenney 为主）占位，Poly Haven 高模只作少量 hero
  • 不做完整的资产库服务 / 数据库——过重，本项目产出量级不需要。替代：JSON + 内容寻址 + 离线看板
  • 不采用 OTIO 全量作为时间线模型——OTIO 是剪辑时间线（track / clip / source range），我们是镜头生成时间线（相机轨迹 + 条件序列），语义不同。替代：借字段命名与「外部引用」概念，自建 shot spec
  • 不在本机跑下游预训练检测器（HED / Midas / OpenPose）——我们输出的是「喂给下游的图」，且违反不下载模型权重纪律。替代：关键点图由 SOMA 关节导出，线稿由 face_id 取轮廓
  • 不用 Blender 做条件图渲染运行时——bpy 5.0.0 本机实测可用，但启动开销大、结果与 numpy 光栅不同源、跨解释器一致性成本高。替代：继续用 numpy z-buffer，Blender 留作下游验证工具
  • 不把语义 seg 扩成 100+ 类的 Segment Anything 体系——我们只有 12 类资产，扩展成本高收益低。替代：保持 12–16 类固定调色板

待拍板的 5 件事（建议进 R0 之前定）

D1 · 镜头库的数据模型

建议 A1：自建 shot spec，只借 OpenAssetIO 的数据模型，不引入外部运行时
选错会怎样：整套引入 OTIO → 管线绑死外部库版本、语义错位（剪辑 clip vs 镜头包），下游接入更慢

D2 · 条件图通道与深度极性

建议 A：六通道，深度改「近=1 远=0」，与评估协议一致
选错会怎样：保持「近=0 远=1」→ 与 resources3D 口径反向，图发给下游容易整个反了还不报错

D3 · 道具零件库来源

建议 A：Kenney 为主 + 少量 Poly Haven hero，特定缺口用纯程序化兜底
选错会怎样：Poly Haven 为主 → 每件 5k–100k 面、要强减面、下载量大；纯程序化 → 品类受限、风格单一

D4 · 资产补全 vs 镜头库谁先

建议 A：镜头库优先（R2 先于 R4）
选错会怎样：资产优先 → 道具缺口补上了，但镜头库拖后，下游能接上的时间点往后推

D5 · 要不要引入 Blender

建议 A：继续只用 numpy z-buffer，Blender 仅人工验证；引入 bpy 作为 R6 可选分支
选错会怎样：引入 bpy → 跨解释器一致性成本 + 启动开销，且渲染结果与 numpy 光栅不同源

J1 · 控制力排序要分通道说

2D 条件图通道：几何 ≈ 动作 ≈ 相机 > 特效。原生 3D / 位姿通道：相机 > 动作 > 几何 > 特效。既有结论「相机与动作最强、体积最弱」成立，但须补「前提」二字。

J2 · 缺的是成套契约，不是通道种类

本项目 depth 为「近=0 远=1」，resources3D 为「近=1 远=0」，完全相反；上轴 Z-up vs Y-up 也相反。混用会静默出错——不报错、结果全错。

J3 · 镜头库按「可校验量」建

社区的镜头预设是给美术用的；我们的镜头库要给验证器用。每个镜头类型必须自带 2–4 个可自动判定的构图 / 运动指标，否则只是「一条好看的关键帧」。

条件图通道补全（最高优先级）

ControlNet 官方 README 自列 9 类条件（canny / M-LSD / HED / scribble / fake-scribble / pose / seg / depth / normal），并点名 HED、Midas、Openpose 三类检测器。resources3D 的评估协议则把下游契约定义为 mask / depth / lineart / shade 四件套，并要求「随图必须带三样东西」：画幅 + 焦距、深度归一化区间、通道语义 + 主体投影口径。两个口径合并即六通道契约。

通道下游对应我们有吗怎么补（复用既有件）
depthControlNet depth / depth_structure_consistency有保留；sidecar 声明 near/far 与极性
normalControlNet normal有保留（含 16bit 无损版）
segControlNet seg有保留；扩到新资产类别（调色板颜色两两不同的约束要保留）
mask主体投影 / 前景遮罩隐含从 depth 前景掩码直接存 8bit PNG，零额外光栅成本
lineartcanny / M-LSD / HED / scribble；edge_consistency无建议移植 resources3D wmcore.line_art_from_face_id（基于 face_id 取轮廓，轮廓纯度更好）

一个镜头包 = 一个自包含目录

shots/<shot_id>/
├── shot_spec.json          # 场景 + 角色 + 相机 + 时间段 + 状态
├── camera/
│   ├── camera.usda         # USD 相机时序（逐帧时间采样，不抽样）
│   ├── camera.gltf         # glTF camera（perspective + yfov/znear/zfar）
│   └── intrinsics.json     # 逐帧 f_px/cx/cy + near/far + 内外参 R/t（唯一权威源）
├── conditions/             # 逐帧条件序列
│   ├── frame_0000_depth.png / _normal.png / _seg.png / _mask.png / _lineart.png / _pose.png
│   └── sidecar.json        # 画幅+焦距 / near-far / 通道语义 / up_axis
├── geometry/               # 该镜头用到的资产实例（GLB）
├── validation_report.json  # 几何 + 构图 + 运动 + 条件图四类校验
└── contact_sheet.jpg + previs.mp4
两条实现规则（本轮调研新增）：① 恒速推轨用线性插值，缓动只用于「有起停」的镜头，且缓动作用在位移量上而非每帧角度上（作用在角度上会做出弧线）——现有 shot_spec._smoothstep 是无条件缓动，落地时需按 move 类型分档。② 焦距与机身分两张预设表：Lens Settings（焦距 / F 值 / 光圈叶片）与 Filmback（传感器宽高 / Sensor Fit）相互独立（社区同构：Blender 相机 Presets、Unreal Lens / Filmback）；我们已有 sensor_width_mm + focal_mm，只需补 lens_preset / filmback_preset 两个枚举。
为什么必须同时出「条件序列」和「相机参数」：下游视频模型吃的是逐帧条件序列；3D 驱动视频吃的是相机轨迹。只出 PNG 会把焦距与位姿信息丢掉——这正是 §控制信号排序的核心结论。好消息：USD 相机约定（−Z 朝前、+Y 向上）与 glTF 一致，export_usd.py 的 _look_at_rot 可直接复用，不需要转轴。

D1 · 镜头库的数据模型：自造 vs 采用现成

A1（建议）

B

实测：兄弟目录 resources3D/venvs/df/bin/python（Python 3.11.16）里 bpy 5.0.0 可用；该项目的 gallery/manifest.json 记录的渲染器正是 "bpy 5.0.0 (Blender as a Python module)"、"render_device": "CPU"。同目录 venvs/blender-portable/ 与 venvs/openscad-portable/ 的 bin 目录为空，即只有 df 这一套实测可用。

建议：改为「主 .venv（Python 3.13）装不上 bpy；bpy 需装在独立的 Python 3.11 venv 中（本机已有可用实例：resources3D/venvs/df，bpy 5.0.0，CPU）」。这与 paradigms.md §A1 已写明的口径一致——PLAN.md §0 把「主 venv 装不上」说成「本机未安装」，属过度概括。这一改会影响「要不要用 Blender」的决策基础（见 D5）。

M3 · PLAN.md §6 第 1 条（V2b）——状态与实际读数不符

实测：assets/validation/retarget_bvh.json 已存在并有读数：48 帧 / 2.0 s / 脚滑均值 0.0135 m、最大 0.0663 m / 贴地 0.0 / method = semantic_replay，文件内自带与原生步态的对比（shot_001: 0.47 cm mean / 3.03 cm max）；shot003_retarget_pose.npz 已落盘。

M4 · PLAN.md §6 第 6 条——「需减面」部分已完成

实测：public_decimated.json（2026-11-21T13:54:11Z）已记录减面完成：island_tree_01 1,599,403 → 74,097 面；ToyCar 108,936 → 29,998；ambulance 2,804 → 1,497；工具 fast_simplification 0.2.0 + trimesh 5.2.1；结果已落盘 assets/public_normalized/。

M5 · PLAN.md §3 / §5——条件图通道数需要补记

实测：conditions.py 与 shot_spec.py:SUPPORTED_CONDITIONS 都只列 3 个通道（depth/normal/seg）；save_condition_pngs 的 docstring 也写明「把三个通道写成 PNG」。

建议：明确写「当前条件图为 3 通道，尚未包含下游最常用的线稿系与人体姿态；六通道契约见 ROADMAP-IMAGE-VIDEO.md §2.2」，避免下游误以为「条件图四件套已就位」。

M6 · community_assets.md §4——ToyCar 的「用途」需要写准

实测：public_decimated.json 的 parted_detail 给出明确结论：「只有玻璃/车窗类独立件（Glass），车身仍是单网格；玻璃学不出车门，不能治门漂移」。

建议：ToyCar 的用途列改为「仅整体参考 + 材质/相机测试；不可用作部件级条件源（车身未分件，分不出车门）」，并在风险列加一句，避免后续把它当成分件管线的验证样本。

M7 · community_assets.md §5 第 1 条——建议补资产分级口径

建议：补一句分级——「近景主资产」宜明确为 hero 级（≤ 50k 面），其余下载件归 mid/low 级（≤ 5k / ≤ 500 面）；Kenney 单件面数 <1,000 天然落在 low/mid 带，Poly Haven 需减面才能进 mid 带。只改措辞，不改既有结论。

M8 · 新增建议：把「跨项目契约」提升为一等文档

理由：本项目与 resources3D 已在深度极性与上轴上出现相反约定。两份文档各自都正确，合起来会静默出错。最省事的防错手段不是改代码，而是把「深度极性 / 上轴 / 通道清单 / 随图三要素 / 跨边界字段」写成一份共享契约（建议 plans/CONTRACT-conditions.md），并让两个项目的读取端都带校验。

M9 · 「OpenAssetManagement (OAM)」应更正为「OpenAssetIO」

实测：ASWF 名下 OpenAssetManagement / OpenAssetManager 两个仓库地址均为 404，GitHub 仓库检索也返回空（本轮两路独立核对，结论一致）。真正存在并活跃的是 OpenAssetIO（Apache-2.0），定位是「面向媒体生产中工具与内容管理系统的开源互操作标准」。

建议：路线讨论里凡提到 OAM 的，一律改称 OpenAssetIO，并引用其官方插件（USD AR2 / OTIO / ShotGrid / 最小 manager 参照）。意义：它的核心主张与我们高度一致（按身份引用、属性按需解析），直接支持 §Shot / Asset Schema 的 asset_id + version + fingerprint 设计。

M10 · shot_spec.py 的缓动口径需要按镜头类型分档

依据：摄影机运动学的通行实践是——恒速推轨应用线性插值（Bezier/自动手柄会在两端引入缓动、破坏匀速感）；缓动只用于有起停的镜头，且应作用在位移量上而非每帧角度上。官方插值文档本轮被 Cloudflare 挑战拦住，故按通行实践标注、不当权威。

建议：镜头库落地时让 camera.move 显式带 easing（linear / smoothstep / handheld），恒速类默认 linear；保留现有 _smoothstep 作为有起停镜头的默认值，不改既有代码路径，避免影响已验证的竖切片。
